# SOSE v0.9.0 adoption and operations plan

## Milestone

v0.9 should answer a different question from v0.8:

> can SOSE be operated, evolved, diagnosed, and measured safely under real
> adoption pressure?

v0.8 stabilized the library boundary. v0.9 should accumulate the evidence needed
to decide whether the public/persistence contracts are ready to freeze for 1.0.

## Already landed after the v0.8 candidate

- [x] transactional SQLite schema migration registry;
- [x] separate SQLite schema and codec versions;
- [x] tested v1 -> v2 migration with legacy database fixtures;
- [x] read-only durable runtime diagnostics;
- [x] stable diagnostics issue codes;
- [x] reproducible runtime benchmark harness;
- [x] CI benchmark smoke report;
- [x] weekly/manual full benchmark workflow.

## Gate 1 — persistence evolution under adoption

Before adding another database adapter:

- collect repeated benchmark runs for the current SQLite adapter;
- identify whether observed cost comes primarily from snapshot rewrite,
  serialization, locking, or backend execution;
- add at least one realistic multi-process/concurrent-access usage case if real
  adopters need it;
- normalize SQLite storage only when measured or operational evidence justifies
  the migration complexity.

### PostgreSQL entry criteria

A PostgreSQL adapter becomes justified when at least one of these is true:

1. real users need multi-process/networked persistence;
2. SQLite locking/concurrency is a demonstrated limitation;
3. operational requirements need database-managed durability/HA beyond a local
   file;
4. the normalized Persistence mapping is stable enough that PostgreSQL would
   test portability rather than invent a second schema at the same time.

PostgreSQL is not justified merely because it is a common production database.

## Gate 2 — observability

- [x] durable diagnostic snapshots are available through the public API;
- add adapter(s) for logs/metrics/OpenTelemetry only if users need push-based
  telemetry;
- preserve a dependency-free core diagnostic model;
- document support/debug bundles if operational incidents produce repeated
  troubleshooting needs.

## Gate 3 — performance evidence

- [x] benchmark workload definitions are versioned;
- [x] reports include environment metadata and machine-readable JSON;
- gather repeated full-suite results before making throughput claims;
- establish trend comparison guidance after enough comparable runs exist;
- add performance regression thresholds only for dedicated/stable runners, not
  shared correctness CI.

## Gate 4 — compatibility evidence

- keep `sose.api` anti-drift tests green;
- document every public breaking change and migration path;
- exercise at least one real deprecation cycle before 1.0 if a public symbol
  must be replaced;
- preserve SQLite schema migration coverage for every schema bump;
- prove release artifacts upgrade across at least two consecutive minor
  versions.

## Gate 5 — 1.0 decision

v0.9 is complete when the project can answer the 1.0 checklist in
`docs/architecture/version-1-readiness.md` with evidence rather than intent.

## Explicit non-goals

v0.9 does not require:

- more industry References unless a genuinely new architecture assumption needs
  falsification;
- PostgreSQL without the entry evidence above;
- automatic telemetry SDK dependencies;
- distributed execution;
- a generic Money, TemporalCapacity, QualifiedResource, or inventory-ledger
  primitive;
- absolute performance SLAs from shared CI runners.
