# SOSE v0.8.0 release closure

v0.8.0 closes the **library stabilization** milestone that followed the v0.7
durable-runtime boundary.

The release does not add one defining core primitive. Its result is stronger:
the existing durable architecture survived broad cross-domain pressure, a real
external persistence boundary, built-artifact installation, repeated recovery,
and an explicit public API contract without requiring premature generic
abstractions.

## Milestone result

The central architectural rule remains:

```text
domain owns meaning
core owns durable mechanics
backend owns ephemeral execution
```

v0.8 makes that rule usable as a library contract rather than only an internal
design principle.

## Public API stabilization

`sose.api` is now the compatibility-relevant domain-author facade.

It exposes the concepts required to assemble a backend-neutral runtime,
including:

- SimulationClock;
- SimulationContext;
- Scheduler;
- Engine;
- deterministic RandomSource;
- Entity, EntityType, and DomainRegistry;
- probabilistic transition decorators;
- Scenario triggers/effects;
- Persistence / UnitOfWork protocols;
- MemoryPersistence and SQLitePersistence;
- backend-neutral temporal/resource/store/container protocols.

An executable anti-drift test pins the facade.

Existing lower-level module imports remain available. The release documentation
classifies them as public, advanced, compatibility-only, or internal rather than
removing them.

## Persistence portability

SQLitePersistence is the first external transactional persistence adapter.

It proves that SOSE durable truth survives:

```text
Python objects
    -> tagged JSON
    -> SQLite transaction
    -> connection close
    -> new process-equivalent adapter instance
    -> runtime/backend rebuild
    -> semantic continuation
```

The reusable PersistenceConformanceSuite runs unchanged against both Memory and
SQLite persistence.

The initial SQLite implementation stores one tagged semantic snapshot per
database. This is intentionally a correctness-first storage layout, not a claim
of production query scalability. Future normalized storage may evolve behind
the same Persistence protocol.

The durable codec avoids pickle and preserves supported semantic Python values,
including dataclasses, exact float bit patterns, datetime/date, enums, UUIDs,
bytes, tuples, sets/frozensets, and mappings.

## Distribution and release validation

CI now validates the artifact users would install, not only editable source.

Every change must pass:

- Python 3.12 test suite;
- Python 3.13 test suite;
- Python 3.14 test suite;
- branch coverage >= 80%;
- wheel and source-distribution build;
- built-wheel installation in an isolated environment;
- installed package metadata/import smoke checks.

A separate release-candidate workflow validates version/tag/release-note
consistency and uploads candidate artifacts.

It deliberately does **not** publish to an external package index. Publishing is
an explicit repository/operator action after trusted publishing configuration is
established.

## Runtime hardening

v0.8 adds semantic stress evidence beyond narrative happy paths:

- repeated backend rebuilds at the same durable boundary;
- deterministic replay of larger same-time scheduled batches;
- stale scheduled ownership remaining harmless after committed execution;
- equal-priority Resource contention and deterministic waiter promotion;
- Priority Store selection under higher cardinality;
- terminal ownership and cleanup after stress flows.

These are correctness tests, not performance benchmarks.

## Cross-domain abstractions deliberately not promoted

### Money

The monetary References now provide currency provenance, integer-minor-unit
allocation where arithmetic occurs, fractional-minor-unit rejection,
odd-cent preservation, restart-safe application, and a float-facing validation
window capped below half a minor unit.

A core Money type is still not justified.

Reopen only when independent domains require a repeated contract such as
currency-specific scale, FX, rated usage, tax allocation, or immutable ledger
posting.

### Temporal capacity

Field Service and Hospitality both require interval overlap, but their durable
ownership lifecycles differ materially. No generic TemporalCapacity primitive is
promoted.

### Qualified resources

Field Service demonstrates skill/territory/window eligibility while the core
Resource lifecycle continues to own capacity mechanics. One domain does not
justify a generic QualifiedResource abstraction.

### Generic inventory ledger

Warehouse distinguishes allocation ownership, physical projection, and immutable
movement/correction evidence without requiring a new core ledger abstraction.

## Adoption path

A deliberately small `tutorial_job` domain now shows the shortest complete
flow:

```text
Entity
-> StateChart
-> public runtime construction
-> immediate Command
-> durable ScheduledWork
-> backend rebuild
-> same semantic result
```

The getting-started guide then points readers to larger References only when they
need the corresponding semantic pattern.

## Compatibility

### Preferred public surface

New domain/integration code should prefer `sose.api`.

### Scheduling

New code must schedule through `context.schedules`.

`context.scheduler` remains compatibility-only and is not the durable
scheduling contract.

### Concrete backends

Concrete optional backends remain explicit imports. For example:

```python
from sose.backends.simpy import SimPyBackend
```

SimPy-native continuation state remains non-durable.

### SQLite type paths

The v0.8 tagged codec restores dataclass/enum types from module + qualified name.
Moving persisted domain classes is therefore a persistence compatibility concern
and should be treated as a migration.

## Release gates

The v0.8.0 candidate is ready for tagging only when the release commit itself is
green for:

- Python 3.12 / 3.13 / 3.14;
- coverage >= 80%;
- distribution build;
- built-wheel installation smoke test;
- version consistency at 0.8.0;
- release-candidate metadata validation for tag `v0.8.0`.

## Explicitly deferred

v0.8.0 does not include:

- automatic PyPI publishing;
- PostgreSQL persistence;
- distributed execution;
- a broad workflow DSL;
- a core Money type;
- a generic temporal-capacity abstraction;
- a generic qualified-resource abstraction;
- claims of performance/scalability from semantic stress tests.

## Next milestone

The next phase should be driven by real adoption and measured operational needs.

Good candidates include:

- publishing/installation feedback;
- schema migration/versioning for external persistence;
- PostgreSQL only after SQLite usage validates the Persistence boundary;
- measured performance benchmarks;
- diagnostics/observability around durable recovery;
- 1.0 compatibility criteria.

Another industry Reference should be added only when it can falsify an
architecture assumption not already exercised by the current catalog.
