# SOSE v0.8.0 stabilization plan

## Milestone

v0.8.0 shifts SOSE from **architecture discovery through domain pressure** to
**library stabilization**.

The domain frontier has demonstrated that the durable core can express materially
different semantics without promoting premature cross-domain abstractions such as
Money, QualifiedResource, TemporalCapacity, or a generic inventory ledger.

The next question is therefore not "which sector should be added next?" but:

> can another engineer install, extend, persist, upgrade, and diagnose SOSE using
> a documented compatibility contract?

## Planned gates

### 1. Public API contract

- [x] classify public, advanced, internal, and compatibility-only surfaces;
- [x] add executable anti-drift evidence for the documented public surface;
- [x] document deprecation expectations before 1.0.

### 2. Persistence portability

- add SQLite as the first external transactional persistence adapter;
- run the reusable persistence conformance suite unchanged against it;
- prove representative restart/reference flows survive process-independent
  serialization rather than only in-memory object copying.

### 3. Distribution

- build wheel and source distribution in CI;
- install the built wheel rather than only editable source;
- run version/import smoke checks against built artifacts;
- define a release workflow that separates validation from publishing.

### 4. Adoption

- provide a deliberately small tutorial domain;
- document the authoring rule: domain owns meaning, core owns durable mechanics,
  backend owns ephemeral execution;
- provide a shortest-path guide from entity/statechart definition to restart-safe
  execution.

### 5. Hardening

- repeated-restart equivalence beyond a single rebuild;
- deterministic replay checks;
- duplicate callback/retry safety at durable boundaries;
- stress important Store/Resource/ScheduledWork invariants.

## Explicit non-goals

v0.8.0 does not require:

- another industry Reference;
- a core Money type;
- a generic temporal-capacity abstraction;
- distributed execution;
- a PostgreSQL adapter before SQLite validates the persistence boundary;
- a broad workflow DSL.

## Release criterion

The version remains `0.7.0` while these gates are under construction.

Only when the stabilization gates are green should project metadata be changed to
`0.8.0`, the plan converted into a completed `v0.8.0.md` closure document,
and the release tagged.
