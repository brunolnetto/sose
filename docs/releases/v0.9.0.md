# SOSE v0.9.0 release closure

v0.9.0 closes the **adoption and operations** milestone that followed the v0.8
library stabilization (`docs/releases/v0.9.0-plan.md`).

v0.8 made the durable architecture a library contract. v0.9 makes it operable by
more than one runtime at a time, and it is the first release whose compatibility
story is proved from the previous release's real artifacts rather than asserted.

## Milestone result

- **One execution model.** Every live runtime is explicitly owned (ADR-0009).
  Organizations, jobs and workers can share a namespace without sharing a clock,
  a writer epoch or scheduled work.
- **Two durable backends with one fencing contract.** SQLite and PostgreSQL both
  offer namespace-wide and job-scoped writer leases with identical semantics.
  A conformance suite runs the same scenarios against both.
- **Operational composition.** Organizations exchange boundary messages
  (ADR-0006) under explicit admission (ADR-0008). PC6 durable recovery resumes
  cross-domain work, and composition flows record a typed causal DAG that the
  causal audit can check end to end.
- **An enforced structural quality floor** (ADR-0010) and an explicit
  deprecation policy (ADR-0011).

## Breaking changes and migration from 0.8

This is a minor release before 1.0. Per `docs/releases/release-policy.md` it may
evolve public APIs; every change below has a migration path.

### Public API (`sose.api`)

No 0.8 name was removed: all 26 remain, and 39 were added. Two contracts changed:

| 0.8 | 0.9 | Migration |
|---|---|---|
| `Engine(context=…, registry=…, persistence=…)` | `owner_id=` is required | pass the stable identity of the runtime's owner; it must not change across that runtime's recovery lifetime |
| `Persistence` / `UnitOfWork` position, committed tick and scenario state were namespace-wide | `get_/set_simulation_position`, `get_/set_scenario_state`, `set_committed_tick`, `committed_tick`, `count_events` take `owner_id=` | custom adapters store these per owner; callers pass the engine's owner |

Builtin domain factories (`build_runtime`, `seed_*`) follow the same rule and take
`owner_id`.

### Durable data

A SOSE 0.8 SQLite database holds an **unowned** runtime snapshot. 0.9 does not
adopt unowned history (ADR-0009):

1. Opening it raises `LegacyUnownedSnapshotError`, naming the unowned fields, and
   leaves the file byte-identical. Before 0.9 this surfaced as an internal codec
   `TypeError`.
2. Stop every worker, then migrate offline into a **new** database:

   ```sh
   sose migrate-owners --sqlite state/old.sqlite3 \
     --output state/owned.sqlite3 --owner <owner> --report migration.json
   ```

   The migration:
   - preserves every identity and adds only the owner;
   - requires the semantic digest of everything else to be unchanged;
   - keeps `old.sqlite3.pre-owner-migration`;
   - deletes its output if the runtime diagnostics report any issue.
3. Point the runtime at the new database with the same `owner_id`.

The SQLite snapshot codec is now version 2. A snapshot that is already
owner-qualified but was written by a pre-release build (codec 1) is accepted and
re-stamped.

### Deprecated, removed in 0.10.0

Each emits a `DeprecationWarning` at the caller that names the replacement:

- `TradingCustomerRecoveryRunner` without `resource_policies`, and the SQLite path
  of `sose composition-recovery`. From 0.10, composition recovery requires
  PostgreSQL (`--postgres-dsn`, `--resource-policies`).
- `PersistentJobRunner` on persistence without scoped writers.
- Importing a name from the module it was split out of during the quality-ratchet
  refactors.
- Publishing a boundary message that has a `causation_id` but no
  `causation_kind`.

## Release gates

| Gate (v0.9.0 plan) | Status | Evidence |
|---|---|---|
| 1. Persistence evolution | met | PostgreSQL entered on its own entry criteria (multi-process, networked organizations; PC6 and OD-5a). SQLite incremental and PostgreSQL share one record-delta mapping and one fencing contract. |
| 2. Observability | met | durable runtime diagnostics in the public API; no push telemetry until users need it |
| 3. Performance evidence | met by restraint | versioned benchmark workloads with environment metadata; this release makes **no** throughput claim |
| 4. Compatibility evidence | met | `sose.api` anti-drift tests; SQLite migration tests on **real 0.8.0 bytes**; the first deprecation cycle starts in 0.9 and completes in 0.10; the release workflow upgrades a mid-flight job from the real 0.8.0 wheel to this release |
| 5. 1.0 decision | **moved** | the 1.0 checklist (`docs/architecture/version-1-readiness.md`) is the next milestone; this release does not claim it |

Release candidate validation (`release.yml`) covers:
- version, tag and release-note consistency;
- wheel and sdist build;
- clean-install import smoke;
- the previous-minor upgrade gate.

CI runs Python 3.12, 3.13 and 3.14 with a 95% branch-coverage floor.

## Compatibility classification

- **Public:** `sose.api`, the `sose` CLI, and `sose.toml` / `sose` catalog configuration.
- **Advanced:** persistence adapters and their writer-lease APIs, and the composition
  and organizational runtimes. They are supported but more likely to evolve before 1.0.
- **Compatibility-only:** the deprecated surfaces listed above.
- **Internal:** everything else, including private (`_`-prefixed) names.

## Explicitly deferred

- The 1.0 readiness decision (Gate 5).
- Removal of the 0.9 deprecations (0.10.0).
- Typed causation for organizational producers outside composition, and removal
  of untyped publishing (0.10.0).
- Module naming cleanups blocked on open work (#629, #630) and the RNG default
  change (#631).

## Next milestone

0.10.0 removes the 0.9 deprecations and makes composition recovery PostgreSQL-only.
The 1.0 readiness checklist then becomes the release gate.
